# 07 Sliding

## About the pattern

For every key, the job counts the events and adds up their `amount` in a 60-second window that slides every 20 seconds. Windows are aligned to the epoch and use the event time (`event_ts`) of each record. Every event falls into exactly three overlapping windows, so every input record changes three running aggregates.

The job does not wait for a window to close. Each time an input changes a (key, window) aggregate, the job writes the new running values to the output topic. Downstream consumers therefore always see the current count. The last record for a (key, window) is its final value.

For example, take a key `k` with a record at event time 45 s and `amount` 1000.

- The record belongs to the windows starting at 40 s, 20 s and 0 s.
- The job writes three output records, with Kafka keys `k:40000`, `k:20000` and `k:0`. Each carries `count`, `sum_amount`, `window_start_ms`, `window_end_ms`, `in_ts` and `engine`.
- A later record for `k` at 50 s with `amount` 500 updates the same three keys. All three windows now show `count` 2 and `sum_amount` 1500.

At 10,000 input events per second, the job writes about 30,000 updates per second. The input and output definition is in [Benchmark setup](#benchmark-setup).

## Why sub-second processing matters for this pattern

Sliding-window counts are the basis of velocity checks for fraud and abuse. One example is "how many card attempts did this account make in the last minute". A service that authorizes a payment reads the current count for the key. It must answer before the next transaction arrives, so a count that is a few seconds late lets a burst of attempts through. The consumer of each output record is that authorization or abuse service, and its deadline is the time before the next transaction.

Sliding windows suit this better than tumbling windows, because the count does not drop to zero at a window boundary. If the counts are only needed for reports or dashboards, near-real-time streaming into Delta is the better fit. A table that refreshes every few seconds is enough, and it is cheaper to run.

## How each engine implements it

| Engine | Key construct | Details |
|---|---|---|
| Spark Real-Time Mode (RTM) | `withWatermark("event_time", "10 seconds")`, `groupBy(window(event_time, "60 seconds", "20 seconds"), key)`, update output mode | [rtm/README.md](rtm/README.md) |
| Amazon Managed Service for Apache Flink | A regular `GROUP BY` over the key and window start, with the three window starts generated by `CROSS JOIN UNNEST(ARRAY[...])`, written to an `upsert-kafka` sink | [flink/README.md](flink/README.md) |

- RTM runs on DBR 18 LTS (`18.x-scala2.13`) with Photon off, in update output mode. The watermark bounds window state. A window is dropped once the watermark passes its end, and input older than the watermark is discarded.
- Flink does not use the `HOP` window table-valued function, because it emits only when the window closes. The regular aggregation emits an update for every input. The group is the output key `<key>:<window_start_ms>`. That key defines the same groups as (key, window start), and it keeps the changelog to inserts and update-afters, so each input produces one record per window. State is removed by `table.exec.state.ttl` (120 s), not by a watermark. Mini-batch stays off.
- Delivery is at-least-once on both sinks.

## Benchmark setup

This pattern follows the shared rules in [docs/CONTRACT.md](../../docs/CONTRACT.md): the input event (section 2), run parameters (section 5), tuned profiles (section 8) and aggregate correctness (section 9).

| Item | Value |
|---|---|
| Input topic | `rtmpack.07-sliding.input`: the shared event (section 2) plus `amount` (integer cents, 100 to 50,000). No duplicates |
| Output topics | `rtmpack.07-sliding.out.rtm` and `rtmpack.07-sliding.out.flink` |
| Output key | `<key>:<window_start_ms>` |
| Output fields | `key`, `window_start_ms`, `window_end_ms`, `count`, `sum_amount`, `in_ts`, `engine` |
| Windows | 60-second windows sliding every 20 seconds, aligned to the epoch, on `event_ts`. Each input updates three windows |
| Emission | An update each time an input changes a (key, window) aggregate |
| Rate | 10,000 events per second |
| Record size | 1024 bytes |
| Partitions | 8 on input and output topics |
| Key cardinality | 100,000 |
| Duration and warmup | 1800 s, of which the first 300 s are excluded from statistics |
| Correctness rule | The aggregate rules of section 9 apply. The load generator writes the expected count and sum for every (key, window) to `results/<run_id>.expected.*`. The collector compares the final update of each (key, window) (the one with the highest `count`) with the expected values. `missing` is the number of expected (key, window) pairs not seen, and `value_errors` is the number whose final values differ |
| RTM sizing | 4 workers of m5.xlarge (16 slots). 8 source tasks plus 4 shuffle tasks is 12 tasks, 75 percent of the slots. Trigger `realTime="5 minutes"`, `linger.ms = 0` |
| Flink sizing | Parallelism 8, 1 parallelism per KPU: 8 KPUs plus 1 orchestration KPU. Checkpoint every 60 s, `linger.ms = 0` |

## How to run

Local tests cover the RTM job, the Flink build and tests, and the harness. Nothing in the cloud is touched.

```sh
infra/scripts/test-pattern.sh 07-sliding
```

The full benchmark run takes 30 minutes at the defaults. Both engines read the same input.

```sh
infra/scripts/run-benchmark.sh --pattern 07-sliding
```

For a short smoke run, add `--rate 2000 --duration 180 --warmup 30`.

### RTM variants

A variant changes one RTM job argument for one run. Pass it with `--tf-var` as `rtm_extra_params`, a map from pattern id to extra arguments. The extra arguments are appended after the pattern's own. A repeated argument takes the last value, so every variant should also set its own `--checkpoint-location`. A checkpoint written with another setting cannot be reused. Use `/Volumes/<catalog>/<schema>/<volume>/checkpoints/` as the path prefix.

| Argument | Default | What the variant changes |
|---|---|---|
| `--state-horizon` | `10 seconds` | The watermark delay, which sets how late an event can arrive and still be counted, and how long window state is kept |
| `--checkpoint-interval` | set by the Terraform batch interval (300 s in the benchmark) | The real-time trigger interval, which is also the checkpoint interval |
| `--kafka-linger-ms` | `0` in the benchmark | The Kafka producer `linger.ms` of the sink |
| `--partitions` | `4` | The number of shuffle partitions for the aggregation. The cluster size is fixed in Terraform, so keep source tasks plus shuffle partitions within the available slots |

This example sets a longer watermark:

```sh
infra/scripts/run-benchmark.sh --pattern 07-sliding \
  --tf-var 'rtm_extra_params={"07-sliding"=["--state-horizon","30 seconds","--checkpoint-location","/Volumes/<catalog>/<schema>/<volume>/checkpoints/07-sliding-rtm-wm30-run1"]}'
```

This example sets a 60 second checkpoint interval:

```sh
infra/scripts/run-benchmark.sh --pattern 07-sliding \
  --tf-var 'rtm_extra_params={"07-sliding"=["--checkpoint-interval","60 seconds","--checkpoint-location","/Volumes/<catalog>/<schema>/<volume>/checkpoints/07-sliding-rtm-ckpt60-run1"]}'
```
